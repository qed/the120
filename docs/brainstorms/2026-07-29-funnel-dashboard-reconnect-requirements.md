# Funnel ↔ Dashboard Reconnect, Step-Back Navigation, and Design Fidelity

## Problem Frame

The First Profit funnel (the "create a business in 10 minutes" flow at `/start` → `/start/children` → `/start/child/[childId]?step=…`) and the parent dashboard (`/dashboard`) shipped as separate efforts and are not stitched together the way the design handoff intended. Three user-facing problems:

1. **Lost families.** A parent who gets partway through the funnel and returns later can land on `/dashboard`, which knows nothing about the in-progress mini-app. It shows the dossier-completion prompt instead of routing them back to the business they were building. The re-entry matrix (`app/lib/funnel/session-rules.ts`) only fires from `/start` and resume links — the dashboard itself has no outbound link into `/start/child/[childId]` at all.
2. **No way back.** Inside the funnel there is no visible way to step backwards through completed steps to review or edit them. The mini-app's step lives in the URL, so browser Back already walks the steps by design (the routing decision recorded in `app/lib/funnel/miniapp-rules.ts`) — but there is no visible affordance; the `/start` explainer/capture is pure component state and forward-only.
3. **Design drift.** Parts of the live flow do not match the design handoff package (`artifacts/First Profit/First Profit application process design handoff/`), a high-fidelity, pixel-perfect spec covering 16 screens — each in exactly one of the two registers, with the 7 mini-app screens additionally specced in both Trail and HQ skins — plus reference screenshots (phone for all screens; desktop for a subset).

The design handoff already specifies the fix for #1: screen 3 ("Dashboard - Add Children") defines state-aware child cards with mono status lines and state-driven CTAs, and its "State-aware resume" rule says child-card CTAs route to the right screen for that child's state. This was designed but never built into `/dashboard`.

## Requirements

Priority order: groups A and D are must-ship (they unblock stranded families), B next, C can land as a separable pass — with the exception that R1's card is built against the handoff's screen-3 spec from the start (see R10). Within group A, R12's Path-register flip is the one non-must-ship piece: it serves only post-arrival families (who are not stranded), so it ships in its own tier that must simply land before the first family reaches arrival, built to the screen-16 spec from the start (same build-to-spec exception as R10).

Definitions: **"arrival"** means the `/start/arrival` acceptance-letter moment — the point where a deposited child's provisioning claim reaches its complete/ready state (`app/lib/funnel/arrival-rules.ts`) and the family holds their @the120.school keys. It is a screen plus a server fact, not an applicant state (`enrolled` is written only by staff promotion and may lag arrival by weeks).

**A. Dashboard ↔ funnel reconnection**

- R1. `/dashboard` child cards become state-aware per the design handoff (screen 3): each card shows the child's funnel/application status line and a state-driven CTA that routes to the correct next screen for that child — START/CONTINUE into `/start/child/[childId]`, dossier wizard, next-steps/reserve, or arrival — matching the handoff's "state-aware resume" rule. Cards cover the **full live applicant ladder** (`added`, `project_created`, `submitted`, `in_review`, `offered`, `waitlisted`, `deposited`, `enrolled` per `app/lib/funnel/applicant-rules.ts`), not just the four states the handoff predates-and-names; status copy for the unspecced states follows the handoff's mono-status idiom, and `waitlisted` must not surface any payment CTA (the applicant-state machine deliberately has no edge from waitlist back to payment). The CTA mapping takes the live-deposit fact as an input alongside `applicant_state`: a `deposited` child with no live paid deposit (refunded — a cohort the state machine deliberately allows to re-reserve) gets the re-reserve card per `canReserveSeatForChild`, never the arrival CTA, which would bounce them in a dashboard↔arrival loop. Cards read `children.applicant_state` directly, not the dashboard's legacy `statusIndex` allow-list. Children with **NULL** `applicant_state` (the entire pre-funnel cohort — NULL is load-bearing per `app/lib/funnel/applicant-rules.ts` and the sync-trigger migration) keep the existing seat-status card rendering unchanged; the state-aware treatment applies only to funnel children, layering on top of `children.status` the same way `canReserveSeatForChild` does.
- R2. Auto-redirect is narrow: a signed-in, funnel-provisioned, non-enrolled family whose resolved child is at `added` (mid-mini-app) is automatically routed back into the flow when they land on `/dashboard`. `project_created` families are NOT redirected — the funnel's reveal deliberately hands off to `/dashboard`, and the dossier wizard that ends the pre-submission state lives there; redirecting them would loop the happy path. They land on the dashboard with a one-click CONTINUE card. ("Resolved child" means the furthest-progressed child per the existing matrix rule; whether that should become most-recently-touched is a deferred planning question.) All other cohorts — password families, enrolled families, and families whose children are all `submitted` or later — land on the state-aware dashboard and reconnect in one click via the card CTA. The dashboard also remains deliberately reachable from within the flow.
- R12. Register for mixed-state families, in two tiers. Must-ship: the dashboard renders in the application register (screen-3 skeleton) and the two registers never mix on one screen; families with no funnel arrival (including pre-funnel/password families whose enrollment predates the funnel) stay in this skeleton indefinitely. Later tier (lands before the first family reaches arrival, built to the screen-16 spec from the start): once the first child in a family — whichever child gets there first — completes arrival (as defined above; not staff-set `enrolled`), the whole dashboard flips to the Path register (screen-16 skeleton). The flip fact is **sticky and monotonic** — "has any child ever completed arrival" (the wrap-U7 arrival account event), not the current provisioning-claim state — so a later refund or mailbox suspension never flips a family's dashboard back. The flip is evaluated per page-load (server-rendered, consistent with R2's no-flash constraint); an already-open tab flips on next navigation, not live. How a still-pre-submission sibling's card renders inside the Path shell has no handoff reference and is a named design decision settled once at planning (default direction: screen-16 card chrome carrying the funnel status line and CTA content), not invented per screen.
- R3. The re-entry rules module (`app/lib/funnel/session-rules.ts`) remains the single source of truth for "where does this family go next," extended rather than duplicated: `resolveReentry` today answers only the family-level question with a fixed screen vocabulary (capture / children_grid / child_resume / sign_in / dashboard / link_expired / link_used — no wizard, next-steps, or arrival destinations), so R1's per-child CTAs require growing that vocabulary and adding a per-child applicant-state → next-screen mapping in the same rules layer. No second, parallel state machine in dashboard components. Two consequences the extension must absorb: (a) the per-child applicant-state → next-screen mapping applies **uniformly across all entry surfaces** (`/dashboard`, `/start`, resume-link redemption): `added` → the mini-app, `project_created` and later → the dashboard, whose state-aware card shows the next step. This deliberately changes today's `/start`/resume landings for post-compose families (they currently land in the mini-app) — once R13 makes the mini-app read-only at `submitted`+, the old landing would strand an offered family in a locked child-skin flow away from their deposit CTA. Uniformity also removes any need to track the requesting surface on resume tokens; (b) new destinations that live inside the dashboard (the dossier wizard has no URL today — it is client view-state in `DashboardApp`) either map to `/dashboard` in `screenRoute` with per-child targeting handled by the dashboard shell, or the wizard gains a child-scoped URL — decided at planning, but named here because every `screenRoute` caller (including resume redemption) receives the grown vocabulary.

**B. Step-back navigation in the funnel**

- R4. Every built mini-app step (`handoff` → `reveal`) shows a visible ← Back affordance that walks to the previous step (using the existing step ladder), in addition to browser Back continuing to work. The affordance gets one consistent treatment per register — in Path-register screens it uses an existing First Profit DS component/icon slot (no hand-styled element), in application-register screens it sits with the floating nav/progress card — with the exact treatment settled once at planning, not invented per screen. On the first step (`handoff`, which has no previous rung), ← Back exits to `/start/children`: the parent still holds the device at that moment — the register seam is crossed by the step's CTA, not by arriving on it — so backing into the parent-facing children grid is seam-safe.
- R5. The `/start` explainer and capture swipes also get visible back navigation between swipes, in the application register per the same one-treatment rule.
- R6. Revisited completed steps are editable, not read-only. Changing an upstream fact resets dependent downstream draft state (e.g., picking a different door resets template/quiz answers), following the documented rule in `docs/solutions/logic-errors/client-draft-state-scoped-by-a-server-fact-must-reset-when-the-fact-changes-2026-07-28.md`. Downstream server-persisted artifacts (e.g., a composed project) follow the same principle: stale artifacts must not silently survive an upstream change. Disclosure is tiered: cheap pre-compose draft state (template selection, quiz answers) may reset silently, but any edit that would invalidate a server-persisted artifact shows the user what will be reset and requires an explicit confirm before applying; cancel returns them to where they were. The confirm tier's concrete artifact set today is exactly one thing — the composed `projects` row (submission and later are unreachable by editing per R13); "or later" future-proofing is not implied. The confirmation's presentation (modal/inline), copy pattern, and register-appropriate styling are settled once at planning, not invented per screen (same governance rule as R4). Whatever invalidation path planning picks must leave `applicant_state` truthful without adding a regression edge: the child stays at `project_created` with an immediate re-compose obligation (Start-over semantics), never a deleted project under a state that asserts one exists — the state machine is frozen by the scope boundary.
- R7. Back navigation must not create illegal states: steps that are gated (e.g., compose requires quiz answers) keep their gates when reached backwards-then-forwards.
- R13. Edit horizon: once a child reaches `submitted` or any later applicant state, back navigation remains available for review but editing locks — no upstream edit may invalidate an artifact underlying a submission, offer, or deposit. The lock is enforced at the write path (mutations re-read `applicant_state` at commit time and reject edits at `submitted`+); the read-only presentation is a courtesy, not the guarantee, so a stale tab cannot edit across the boundary. Locked steps are not a dead end: they carry a brief locked-state explanation and a visible route to the admissions change path (the concrete entry point — contact link or reply-to email — confirmed at planning), so review mode ends in an action, not a wall. Post-submission changes go through admissions, not the funnel; the applicant-state machine stays unchanged, consistent with the scope boundary.

**C. Design fidelity to the handoff**

- R8. Conduct a full screen-by-screen audit of the live flow against the handoff package, scoped to the handoff's actual inventory: the application-register screens in that register only (phone reference shots for all, desktop for a subset), and the 7 mini-app screens (handoff → reveal) in both Trail and HQ skins, phone + desktop (reference screenshots in `artifacts/First Profit/First Profit application process design handoff/design_handoff_first_profit/screenshots/` — 19 application-register captures, 14 trail-maya, 14 hq-theo). Output is a concrete deviation list covering layout, tokens (color/type/spacing/radii), copy, and behavior noted in the README. Before the fix pass, each deviation is classified as **drift** (fix it) or **decision** (a deliberate divergence — evidenced by reviewed code comments, `docs/solutions/` entries, PR discussion, or the R-rules); ambiguous cases are escalated to Peter rather than defaulted either way.
- R9. Fix every deviation found, honoring the handoff's fidelity rules: pixel-match except listed prototype scaffolding; the two-register seam preserved; copy rules applied (no em dashes, "complete" not "sealed", "Not Yet" never "failed", no emoji outside the First Profit DS iconography).
- R10. The state-aware dashboard cards built under R1 are styled to the handoff's screen-3 spec from the start (status line, DOSSIER % bar, band note, state CTA placement/colors) so the card isn't touched twice. This is a build-to-spec rule only — the reconnection work (A, D) does not wait on, or travel with, the full audit/fix pass (C).

**D. Returning without a session (adjacent gap, confirmed in scope)**

- R11. The `/dashboard` sign-in screen offers an "email me a link to continue" affordance alongside email+password, so a funnel-provisioned family (account created with an undisclosed random password) can get back in without the password-reset detour. It reuses the existing resume-token machinery (single-use, 60-minute links) and preserves its anti-enumeration behavior across the full observable contract, not just response bodies: the sign-in entry point invokes the existing hardened request path (`requestResumeLinkCore`) directly, with no additional branch-specific work between known- and unknown-email outcomes (no awaited side effects, differing error handling, or divergent client transitions), preserving the constant-response, latency-equalized, rate-limited contract end to end (per `docs/solutions/security-issues/constant-response-is-not-constant-timing-and-a-guard-moves-when-you-extract-2026-07-27.md`). The sign-in entry point consumes the **same** rate-limit buckets (email- and IP-keyed) as the existing `/start` resume-request path — no parallel or additional limiter, so the two surfaces cannot be combined to multiply an attacker's attempt budget against one email. Expired or already-used links land on the existing `link_expired` / `link_used` screens, which offer re-requesting a fresh link.

## Success Criteria

- A parent who abandons the flow mid-mini-app and returns later (via sign-in, direct `/dashboard` visit, or resume link) ends up back in the flow for the right child within one click or zero clicks — never stranded on a dossier prompt with no path back.
- From any built funnel step, a parent can walk backwards to the first step and forwards again without losing legal state; for a pre-submission child they can change an earlier answer with downstream state resetting coherently (with confirmation where a persisted artifact is at stake), and for a `submitted`+ child every step renders read-only with a visible route to the admissions change path.
- The deviation audit exists as a written checklist, and after the fix pass, each item is either fixed or explicitly waived with a reason.
- A funnel family with an expired session can re-enter from the dashboard sign-in screen using only their email.

## Scope Boundaries

- No changes to the funnel's step ladder, applicant-state machine, or conversion points (C1–C4) — this is stitching and fidelity, not funnel redesign.
- No resume-position-in-URL: the existing rule stands (server resolves the furthest child; deep-linking a resume to a specific `?step=` stays out of scope).
- Prototype scaffolding in the handoff (navigator rail, stage headers, phone bezels, fast-forward buttons) is explicitly not product UI and is not built.
- The landing hero photography ("request final art") remains an open asset question, not a code deliverable here.
- No changes to Stripe checkout internals beyond fidelity of the surrounding screens.

## Key Decisions

- **State-aware cards + narrow auto-redirect (not either/or):** the dashboard becomes the hub the design intended, and the redirect covers only the cohort it can serve correctly — funnel-provisioned, non-enrolled families with a pre-submission child. Review consensus (adversarial, feasibility, product-lens) was that a blanket redirect is unachievable under the re-entry matrix's priority rules and would fight the multi-child hub; everyone else reconnects in one click via the card CTA.
- **Edit horizon locks at submission:** back navigation stays for review, editing stops at `submitted`+. No upstream edit may invalidate an artifact underlying a submission, offer, or deposit; post-submission changes go through admissions. Keeps the applicant-state machine untouched.
- **Mixed-state families — register flips at first arrival:** the dashboard is application-register until the first child completes arrival (provisioning claim complete — the concrete server fact, not staff-set `enrolled`), then flips whole to the Path register on next page-load. Per-card register mixing was rejected as violating the handoff's seam rule. The flip itself is a later tier than the must-ship reconnection work, since post-arrival families are not stranded.
- **Resume tokens over native Supabase magic-link for R11:** the resume machinery already wraps magic-link issuance behind a hardened anti-enumeration, rate-limited request path and lands users through the re-entry matrix; native magic-link sign-in would bypass both. The 60-minute single-use contract is affirmed for the sign-in screen (a fresh link is one request away).
- **Full back + edit with reset rules (not read-only review):** revisiting completed steps allows editing; the codebase already documents the reset-on-upstream-change rule, so the safety concern is handled by an established pattern rather than by locking steps.
- **Full audit then fix (not spot fixes):** the handoff is pixel-fidelity; drift the user hasn't noticed is still drift. The audit doubles as the acceptance checklist for the fix pass.
- **Sign-in gap in scope:** "reconnect the dashboard to the flow" fails for exactly the users most likely to need it (funnel-provisioned, session expired) if the only door is a password they never had.

## Dependencies / Assumptions

- The handoff package at `artifacts/First Profit/First Profit application process design handoff/` is the authoritative design source; where it conflicts with the live implementation, the handoff wins unless a deliberate decision superseded it — and "deliberate" includes decisions recorded in reviewed code comments (e.g., `app/lib/funnel/miniapp-rules.ts`'s D9-confirmed notes), `docs/solutions/` entries, and PR discussion, not only brainstorm docs like the R-rules in `docs/brainstorms/2026-07-27-first-profit-funnel-requirements.md`. Conflicts found during the audit get surfaced (drift vs. decision per R8), not silently resolved.
- Existing machinery assumed reusable and verified present: re-entry matrix (`app/lib/funnel/session-rules.ts`), step ladder (`app/lib/funnel/miniapp-rules.ts`), resume tokens (`funnel_resume_tokens` + `app/lib/funnel/resume-core.ts`).
