# New User Flow v3 (The120 → First Profit)

## Problem Frame

The current live signup ("v2", at `/start` in The120) is application-shaped: a parent
fills out a per-child application, submits it for review, and waits on next-steps/
waitlist. The new flow ("v3") replaces it with a kid-first, story-driven onboarding
based on the Magic Patterns prototype in `artifacts/New Login Flow Aug 2026`: the
parent adds their kid, an AI-drawn comic cover makes the kid the hero of their own
First Profit graphic novel, optional story questions become page 1, and a real
account is provisioned in the same sitting — no review gate, no waitlist.

This is also a strategic separation: The120 becomes the signup/account front door
for the school's apps (First Profit today; fast math, math, and others later), and
individual apps are accessed separately in their own codebases (First Profit at
firstprofit.school). All First Profit UI surfaces on the120.school are deleted as
part of this work (as a separable follow-on step — see Phasing).

This is a hard launch: after it ships there is exactly one new-user flow, v3 at
`/start`, for ALL families — brand-new, mid-application, waitlisted, and existing
beta families alike. The v2 flow is archived (hidden, not deleted, unrouted).

## Flow Overview

```
/start (The120)
  1. Parent step ─ parent full name + email + password + consent
                   → 6-digit code emailed, typed inline (email verified,
                     parent session created — still one sitting)
  2. Add kid ───── kid name + age
  3. Cover ─────── photo upload (optional) → REAL AI comic cover generation
                   (progress animation; no photo → cover personalized from
                   name/age/answers instead)
  4. Page 1 ────── 6 story questions (optional, skippable)
  5. Account ready─ auto-generated username + password shown, real account provisioned
        │
        ├─ "Keep building" → firstprofit.school in a NEW TAB, auto-signed-in
        └─ original tab → parent dashboard (add 2nd kid → re-enter kid flow at step 2)

Returning family (any v2 state) → logs in → routed into v3 at their first
missing step, with known data pre-filled/skipped.
```

## Requirements

**Parent step, verification, and consent**
- R1. Step 1 collects parent full name, email, a parent-chosen password, and
  consent before any kid content is entered or generated. The consent must
  explicitly cover: (a) creating an account for their child, (b) uploading their
  child's photo and processing it via a third-party AI image service — including
  future photo uploads for cover regeneration initiated later from inside First
  Profit (the deliberate basis for the kid-usable R5 add-photo hook) — and (c)
  storing the child's answers and generated cover on the child's profile
  (including the pre-provisioning draft record, R18).
- R2. Email verification happens inline in the same sitting: a 6-digit code is
  emailed and typed on step 1, which verifies the email and creates the parent
  session before the kid-first steps begin. No click-a-link round trip. The
  parent later signs in with email + password (with a reset flow).
- R3. After the first kid finishes the flow, the parent lands on the existing
  The120 parent dashboard (`app/dashboard`). Its existing add-child entry
  (`ADD_CHILD_HREF = "/start/children"` in `app/dashboard/DashboardApp.tsx`) is
  retargeted to re-enter the v3 kid-first flow (step 2 onward) under the same
  parent — a retarget of the current v2 deep link, not a new addition.

**Kid-first onboarding (per kid)**
- R4. Add-kid step: kid full name + age (5–18 validation as prototyped). Full
  name (not just first name) is deliberate: the account serves the school across
  apps.
- R5. Cover step: a comic-style cover is generated by a real AI image model
  during onboarding, with the prototype's staged progress animation covering
  actual latency. With a photo, the kid is drawn as the hero. WITHOUT a photo the
  cover is still AI-personalized from what the flow knows (name, age, story
  answers so far) — a designed experience, not a generic placeholder — and both
  the parent dashboard and First Profit offer an "add photo" hook later that
  regenerates the cover with the kid as the hero. Photo uploads are validated
  (image type, size limits) before anything is sent to the vendor.
- R6. Story step: the 6 story questions from the prototype
  (`src/data/storyQuestions.ts`) are presented as "page 1" of the kid's journey.
  Answers are optional/skippable — account creation is never blocked on them.
  Answers that are given are stored on the kid's profile.
- R7. Account-ready step: shows the kid's auto-generated credentials with
  copy-to-clipboard:
  - Username: `firstname.lastname@firstprofit.school` — deliberately the kid's
    future real school email address across the school's apps.
  - Password: `iloveschool<word>` where `<word>` is drawn from the kid's answers
    (always ≥11 chars, satisfying the existing `STUDENT_PASSWORD_MIN_LENGTH = 10`
    floor in `app/fp/lib/provision-rules.ts`); when answers are skipped the
    fallback `<word>` is randomly selected per kid (never one shared constant
    across accounts — predictable username + constant fallback would mean
    no-secret authentication for skippers) and non-name-colliding.
  - Username collisions are resolved automatically by adapting the existing
    tested collision primitive (`generateUsernameBase`/`mintUsername` suffixing
    in `app/fp/lib/fp-username-rules.ts`) to the email-shaped format, and the
    final username is shown plainly to the family (no silent surprise).

**Account provisioning and handoff**
- R8. The account is real and live in the same sitting: provisioning invokes the
  existing shared server-side cores (`app/api/fp/signup/signup-core.ts`,
  `child-core.ts`) directly from the v3 flow (same repo — not the CORS HTTP
  routes, whose Origin allowlist is scoped to firstprofit.school). No review
  gate, no waitlist, no staff acceptance step. Consent + inline verification
  (R1–R2) satisfy the existing consent/verify gates rather than bypassing them.
- R9. Launch-time abuse caps reuse the existing rate-limit machinery
  (`app/fp/lib/rate-limit-*`): per-IP/per-email limits on signup, a strict
  attempt/lockout cap on 6-digit verification-code entry (its own limit — a
  6-digit space inside the verify TTL needs more than signup-initiation
  throttling), and a small per-kid cap on cover generations. Invisible to real
  families.
- R10. "Keep building" opens firstprofit.school in a NEW tab with the kid already
  signed in (one-time auto sign-in handoff). The handoff token MUST be
  single-use, short-TTL, bound to the specific kid account, and carried in a
  channel that doesn't leak (not a plain URL query string, which lands in
  browser history, server logs, and Referer headers — e.g. fragment- or
  POST-based delivery exchanged immediately for a session). The shown
  credentials are for future logins. The original tab continues to the parent
  dashboard.
- R18. Because the paid AI generation (step 3) and story answers (step 4)
  precede provisioning (step 5), a server-side DRAFT record exists before the
  kid account does. It is a named part of the design: it holds the photo,
  generated cover, and answers; it is the key for the per-kid generation cap
  (R9) and the mid-flow resume (R14); the R1 consent covers it; and abandoned
  drafts (never reaching step 5) are cleaned up on a defined retention schedule
  (period decided in planning) so minors' photos are not stranded in limbo.

**Returning families (hard launch)**
- R11. When any existing family logs in — mid-application, waitlisted, or live
  beta — they are routed into the v3 flow at their first incomplete step, with
  steps they've effectively completed skipped or pre-filled from existing data
  (e.g. skip parent account creation; pre-fill child name/age). Families with
  fully-provisioned kids land on the parent dashboard. At launch, a one-time
  announcement email goes to mid-application, waitlisted, and beta families —
  instant signup is open, with a link that lands them in this resume flow.

**Cover inside First Profit**
- R12. The generated cover is stored on the kid's profile and this build also
  surfaces it inside the First Profit app (first-profit repo), e.g. on the kid's
  home/journey surface, where it can later be modified (add/replace photo,
  regenerate).

**Free trial messaging**
- R13. The flow and/or parent dashboard communicates that this is a free trial
  with a paid conversion later. Messaging only in this build — no trial timers,
  enforcement, or payment path yet — and the copy stays terms-neutral (no implied
  trial length, no "free while in beta" framing) so it doesn't constrain the
  future monetization model.

**Edge states (must be designed, not improvised)**
- R14. The following states have explicit designed behavior: provisioning
  failure (network/backend error at account-ready); new-tab handoff blocked
  (mobile popup blockers) or token expired — with a visible manual fallback
  link; the handoff button while the first-profit side hasn't shipped token
  consumption yet (phase-gap state); verification code never arrives — resend
  with cooldown, edit-email-and-resend before verification, and code-expired
  behavior (existing verify-store TTL is 60 minutes); step-1 email already
  registered — route to sign-in (with reset) and then into the R11 resume
  logic; mid-flow refresh/abandonment — progress persists server-side once a
  paid AI generation has run; back-navigation to correct earlier entries;
  dashboard kid-list states (none / in-progress / complete, multiple kids).

**Archival and cleanup**
- R15. The v2 flow's code moves to `archive/new-user-v2/` in The120 — preserved
  for reference, with no routes pointing at it. The v3 flow takes over `/start`.
  The archive directory is excluded from tsconfig, lint, and the test runner so
  the moved code (which imports live modules such as `@/app/dashboard`) cannot
  break builds or silently keep tests running against it.
- R16. All First Profit UI surfaces on the120.school are deleted: the `app/fp` UI
  trees (`(app)`, `(auth)`, `fw`, `components`, `content`, layout) and
  `app/first-profit`, plus any nav/links to them. `app/fp/lib` is NOT UI — it is
  shared infrastructure imported by the kept `app/api/fp/*` routes and the cron
  routes (provision-core, provision-rules, fp-username-rules, rate-limit-store/
  rules, parent-email, notify, evidence-loader, and more) and must be relocated
  (e.g. under `app/api/fp/` or `app/lib/`) before the UI tree is deleted. The
  `app/api/fp/*` backend stays — The120 remains the account/provisioning backend
  that firstprofit.school talks to. Before deletion, audit the URLs the beta
  cohort's onboarding materials, nurture emails, and bookmarks reference and
  redirect any that fall in the deletion set.
- R17. After this ships there is exactly one new-user flow. Existing entry points
  that link to `/start` itself (landing CTAs, emails) need no URL changes, but
  the v2 deep routes (`/start/children`, `/start/child/[childId]`,
  `/start/review`, `/start/next-steps`, `/start/waitlist`, `/start/arrival`)
  disappear — inbound links to them (dashboard, sent emails, bookmarks) are
  retargeted or redirected.

## Phasing

Two separable shipments, in this order:
1. **The v3 flow** (R1–R14, R15, R17) — ships when ready.
2. **FP-surface deletion** (R16) — its own step after the flow is live; neither
   blocks the other.

## Success Criteria

- A new parent can go from landing on `/start` to their kid inside First Profit,
  signed in, in a single sitting — the only wait is typing the emailed 6-digit
  code.
- Every kid gets an AI-personalized cover — from their photo when provided,
  from their name/age/answers when not — visible during onboarding and inside
  First Profit.
- A parent can add a second kid from the dashboard and repeat the kid flow
  without re-entering their own details.
- Any existing family (mid-application, waitlisted, beta) that logs in is routed
  into v3 at the right step with their known data pre-filled; no family is
  stranded in a dead v2 state.
- (Phase 2) No First Profit UI is reachable anywhere on the120.school; the v2
  flow is unreachable but its code is intact under `archive/new-user-v2/`; no
  beta-family bookmark or nurture-email link 404s.

## Scope Boundaries

- No trial mechanics (length, expiry, lockout, checkout) — messaging only (R13).
- No staff review/admission tooling for v3 signups; the old review surfaces are
  not ported.
- No changes to First Profit's login model (username + password) beyond the
  one-time auto sign-in handoff and cover display/modification.
- The v1 application flow (basics/academics/interests/projects) is history and
  not part of this work.
- Backend `app/api/fp/*` endpoints are kept, not redesigned (extend only as
  needed for v3 provisioning, inline code verification, parent password reset,
  auto sign-in tokens, and cover/answer storage).

## Key Decisions

- **Real AI cover generation, synchronous, for every kid**: generation happens
  during onboarding with the progress animation covering real latency — the
  magic moment is the point of the flow, and the no-photo path is a designed
  personalized experience, not a degraded fallback.
- **Inline 6-digit email verification**: keeps verifiable parental consent (which
  gates a minor's photo going to an AI vendor) without breaking the
  single-sitting promise. Parent authenticates thereafter with email + password.
- **Kid usernames are future school emails**: `firstname.lastname@firstprofit.school`
  is deliberate — one identity across the school's apps, and the username IS the
  mailbox address the school will eventually provision. Password
  `iloveschool<word>` is memorable and clears the existing validator floor.
- **Provision via shared cores, not HTTP**: the v3 flow calls the existing pure
  server-side signup/child cores in-repo, avoiding the Origin-allowlist and CSRF
  questions entirely.
- **Instant access, optional answers**: no admission gate; story answers are
  content, not an application.
- **Hard launch for all families**: one flow; returning families resume inside
  v3 with pre-filled data rather than living in a parallel legacy state.
- **The120 = front door only**: FP UI surfaces on the120.school die (as phase 2);
  apps live in their own codebases; The120 keeps the shared account backend.
- **Versioning**: v1 = original application flow (gone), v2 = current live flow
  (→ `archive/new-user-v2/`), v3 = this build (owns `/start`).

## Dependencies / Assumptions

- Cross-repo work: The120 (flow, archival, FP-surface deletion, provisioning/
  token APIs) and first-profit (auto sign-in landing, cover display/modify).
  Coordinated deploys needed for the handoff and cover features; each side must
  degrade gracefully if the other hasn't shipped yet.
- The `FP_SIGNUP_TEST_ONLY` launch gate (closed by default, OFF in production)
  is enforced ONLY in the HTTP route (`app/api/fp/signup/route.ts`) — NOT in
  `signup-core.ts`. Since v3 calls the cores directly, it is not covered by that
  gate at all: v3 needs its own explicit go-live lever (decided in planning),
  the `is_test` classification must be re-wired on the direct-call path, and
  flipping `FP_SIGNUP_TEST_ONLY` affects only the pre-existing
  firstprofit.school HTTP signup path (a separate, deliberate decision).
- Kid photos are sent to a third-party AI image service. Minimum data-governance
  requirements: the vendor must not retain or train on submitted images (or an
  equivalent DPA is in place), and photos/covers/answers are deletable on parent
  request.
- The existing consent/verify machinery in `app/api/fp/signup` (consent,
  consent-policy, verify routes) is adapted to the inline-code model rather than
  bypassed; the existing per-family child cap (`MAX_CHILDREN_PER_FAMILY`) and
  per-child consent records must support the add-another-kid loop.
- Prototype styling (cream/paper-grain comic aesthetic, framer-motion
  transitions) is the design reference for the v3 flow.
- Trial framing applies to new v3 signups; how it reads to the 10 existing beta
  families (whose nurture sequence is still running) is reviewed as part of the
  R11 returning-family experience.

## Outstanding Questions

### Deferred to Planning
- [Affects R5][Technical] Which image model/provider generates the cover, cost
  per generation, latency envelope, and the failure/retry path when generation
  fails or is slow (flow must still complete with the name-personalized cover).
- [Affects R5][Technical] Where kid photos and generated covers are stored
  (retention, access control for images of minors).
- [Affects R7][Technical] Exact `<word>` extraction and the skip fallback word;
  guard against the existing validator's kid-name-substring refusal.
- [Affects R2][Technical] Where the inline 6-digit code fits the existing
  verify-store machinery (`app/api/fp/signup/verify-store.ts`) vs. a new code
  path.
- [Affects R2/R8][Technical] The shared signup-core delivers the parent session
  as cross-origin JSON tokens (no cookie, by design); decide how the same-origin
  v3 flow mints the cookie session that `app/dashboard`'s gate reads.
- [Affects R8][Technical] v3's go-live lever (new gate in the shared core, env
  flag on the v3 flow, or the deploy itself), given `FP_SIGNUP_TEST_ONLY` does
  not cover the direct-core path.
- [Affects R7][Technical] `mintUsername` derives its base from first name only;
  the `firstname.lastname` local part needs a two-name variant, and the collision
  suffix position within the local part must be decided.
- [Affects R18][Technical] Draft-record retention period and cleanup mechanism
  for abandoned flows.
- [Affects R10][Technical] Auto sign-in token mechanism between the120.school
  and firstprofit.school (issuance, storage, consumption on the Vite side).
- [Affects R11][Technical] Mapping v2 application state → v3 resume point, and
  what the login entry point is for families who never had a parent password.
- [Affects R12][Technical] Where in First Profit the cover surfaces and how the
  Vite app fetches it.
- [Affects R16][Technical] Exact deletion inventory of FP surfaces in The120
  (including `app/fp/fw`, nav links, redirects) and the beta-cohort URL audit;
  `app/fp/lib` also contains fw-* and app-runtime modules (sync-engine,
  offline-queue, skin-tokens, actions/) whose fate — relocate vs delete — the
  inventory must cover.
- [Affects R3][Technical] What the existing `app/dashboard` shows today (it is
  v2-application-shaped, with a gate that may redirect v3 parents) and the
  smallest change that makes it the v3 landing with kids-list +
  add-another-kid.
