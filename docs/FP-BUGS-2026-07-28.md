## 0. Read this before writing any code

1. **`AGENTS.md` is binding.** This is not the Next.js in your training data. Read the relevant guide in `node_modules/next/dist/docs/` before touching routing, caching, Server Actions, or `useRouter`. Several fixes below are specifically about Next 16 router-cache semantics — do not pattern-match from Next 13/14 habits.
2. **`docs/solutions/` is prior art.** Categories: `best-practices`, `build-issues`, `database-issues`, `integration-issues`, `logic-errors`, `runtime-errors`, `security-issues`, `test-failures`, `ui-bugs`, `workflow-issues`. Grep it before diagnosing. Several bugs below have a sibling already documented there.
3. **Testing canon in this repo:** there is **no jsdom**. Components are not unit-testable. Every decision must live in a plain `*-rules.ts` / `*-core.ts` module with its own Vitest harness, and the component must be a faithful renderer that calls into it. If your fix puts a decision inline in a `.tsx` file, it is a decision no test can reach — that is exactly the failure mode the code comments in this repo keep warning about. Move it out.
4. **`"use server"` files stay thin** — gate → zod → authorize → delegate → typed result. They cannot be unit-tested (they import `next/headers`). No type re-exports from them (registers a server reference and takes the whole module down).
5. Verify with `npm test` (vitest) and `npm run lint`. Add tests to the existing `app/fp/lib/__tests__/` suites.
6. **Do not "fix" a check by loosening it.** Two items below (B1, B3) are a spec-vs-implementation conflict where the code is deliberate and documented. Those are flagged **DECISION REQUIRED** — do not silently pick a side.

## 2. Consolidated root causes

Three of the seven blockers and one should-fix collapse into **two** underlying defects. Fix these two and four checks clear.

### RC-1 — `router.push()` immediately followed by `router.refresh()`

Affects **2.5.8, 3.10.2, 2.4.2**.

`FwQuickCreate.tsx:166-167`:

```tsx
router.push(`/fp/fw/cohort/${cohortId}/student/${res.studentId}`);
router.refresh();
```

`FwSignInForm.tsx:36-37` and `ClaimGuideInviteForm.tsx:42-43` have the identical pair.

In Next 16 these two are racing over the same client router cache. `refresh()` invalidates the cache the in-flight `push()` navigation is resolving against; the observable result is the navigation being superseded or re-resolved, so the user stays on the current route (form still open, roster unchanged) and the destination only materialises on a later explicit reload. That is precisely the reported symptom in all three checks.

**Read `node_modules/next/dist/docs/` on `useRouter`, `refresh`, and Server Action revalidation before choosing the fix.** Do not guess the ordering. The two candidate shapes, in preference order:

1. **Server-side redirect.** Move the navigation into the Server Action: `revalidatePath(...)` then `redirect(...)` from `quickCreateFwStudent` / the sign-in action. One round trip, no client cache race. This is the cleanest and matches how the rest of this repo already invalidates (`fw-ops.ts`, `fw-import.ts` both call `revalidatePath`).
2. **Order-corrected client navigation** — invalidate first, then navigate, and only navigate once the invalidation has settled.

**Also missing regardless of which shape you pick:** `app/fp/lib/actions/fw-student.ts` calls **no** `revalidatePath` at all. Every other mutating FW action does (`fw-ops.ts` has 12 call sites, `fw-import.ts` has 2). This is the direct cause of the second half of 3.10.2 — "the record was initially absent from search". Add at minimum:

```ts
revalidatePath(`/fp/fw/cohort/${cohortId}`);
revalidatePath(`/fp/fw/ops/cohort/${cohortId}`);
```

**Effort: ~1 half-day** (both actions + the three client call sites + tests).

### RC-2 — revoked board token renders as an indefinite "connecting" state

Affects **3.5.3, 3.18.2**.

`FwBoard.tsx:134-142`:

```tsx
if (res.status === 404) {
  setFeed(null);
  setStale(true);
  return;
}
```

That is the *correct* security behaviour (it clears children's names from an open projector tab — see the comment). The bug is what happens next: `feed` is now `null`, so line 218 falls to `"Catching up with the room…"`, and `BoardHeader` line 261 renders `"connecting"` because `hasData` is false. The operator gets the cold-start message forever, with no explanation and no recovery step, and the poll loop keeps hammering a dead token every 4s.

**Fix:** add a third terminal state alongside `stale`. On 404: clear the frame (keep that), set `revoked`, **stop the interval**, and render a distinct panel — something like *"This board link is no longer active. Ask The 120 staff for a fresh link."*

**Do not** leak revoked-vs-expired-vs-never-existed. `resolveFwBoardToken` in `fw-board-loader.ts` deliberately collapses all refusals into one bare 404 for anti-enumeration, and `fw-board-rules.ts:160` keeps the distinction server-side only. One generic terminal message for all three is both correct and sufficient for the operator.

Put the state machine in `fw-board-rules.ts` as a pure function (e.g. `fwBoardConnectionState({ httpStatus, hasFrame, lastOkAgeMs })` → `"live" | "catching_up" | "connecting" | "dead_link"`) with a Vitest harness, and make `FwBoard.tsx` render its output. No jsdom means the component itself gets no test — the decision must not live there.

**Effort: ~1 half-day.**

### B7 — 3.18.5 · board cells differ by colour alone (WCAG 1.4.1)
`app/fp/fw/components/board/FwBoard.tsx:320-324` and `:383-389`.

```tsx
function cellClass(state) {
  if (state === "verified") return "bg-verified";
  if (state === "not_yet") return "bg-not-yet";
  return "bg-hq-sunken";
}
```

rendered as `<span title={taskId} className={"inline-block h-2.5 w-2.5 rounded-[2px] " + cellClass(...)} />`. The `title` carries the task id only — no state. Verified, not-yet and untouched are the same 10px rounded square, distinguished only by background colour. No text, icon, shape, border, or `aria-label`.

**Fix, both halves:**
- **Non-colour channel.** Give each state a distinct visual form as well as a colour — e.g. verified gets a filled square with a check glyph or a solid border, not-yet gets a distinct outline/hatch, untouched stays empty with a hairline border. At 10px a glyph may not survive; a border-style + fill-density difference will. Whatever you choose must remain legible from the back of a room at projector distance.
- **Programmatic name.** Add `aria-label` (or `title`) carrying task **and** state, e.g. `"1.2.4 — verified"`. Keep it out of the memo comparator's cost path.

**Watch the Tailwind constraint** flagged in the existing comment at line 317: class strings must be **complete literals**, never concatenated, or the scanner drops them and the cell renders colourless. Extend `cellClass` to return the full literal for each state; do not build strings.

Add the state→presentation mapping as a pure exported function with a Vitest test asserting the three states produce three distinct class strings and three distinct labels.

**Effort: ~1 half-day** including a projector-distance visual check.

### S1 — 2.4.2 · guide landing needs a reload before the roster appears

### S2 — 2.7.4 · no visible First Dollar celebration on the board
The overlay exists and looks correct (`FwBoard.tsx:446-459`, full-screen `fixed inset-0`, 6.5s hold, queued). The counter and ticker updated, so the event was verified, name-bearing, and `isFirstDollarTask` matched. That leaves exactly one filter it can have died on — `fw-board-rules.ts:641-642`:

```ts
const gap = cell.last.atMs - cell.last.capturedAtMs;
if (gap < 0 || gap > FW_FIRST_DOLLAR_FRESHNESS_MS) continue;   // 60_000
```

**Hypothesis (verify before fixing): device clock skew.** `FwTaskView.tsx:286` and `:331` send `capturedAt: new Date().toISOString()` — the guide iPad's clock. `clampFwCapturedAt` (`fw-rules.ts:638`) clamps it to `≤ now`, which handles a clock running *fast*, but a device running **slow by more than 60 seconds** produces `gap > 60_000` and the bell is skipped **silently**. An event iPad off a captive-portal network is exactly the case. This would also explain why repeated observation never produced a moment while every aggregate updated.

**Do this first, before changing any threshold:**
1. Query `path_fw_events` for a recent 1.2.4 checkmark and compute `at - captured_at` directly. If it is > 60s, the hypothesis is confirmed.
2. `runFwCheckIn` already returns `capturedAtClamped` (`fw-checkin-core.ts:459`) — check whether it is being logged. If not, log it; a clamped capture on the online path is an anomaly signal that is currently going nowhere.

**Fix if confirmed:** the online path should not be sending a device timestamp at all. `clampFwCapturedAt` already documents that a *missing* `capturedAt` means "receipt time is capture time" and is the intended 99% shape. The offline queue path (`fw-sync-client.ts:131`) genuinely needs the device stamp; the live tap in `FwTaskView` does not. Stop sending it from the online path and the skew window disappears for live taps.

**Effort: ~0.5 half-day to diagnose, ~0.5 to fix.** Do not widen `FW_FIRST_DOLLAR_FRESHNESS_MS` as a workaround — that weakens the replay-suppression this constant exists for.

### S3 — 3.18.10 · two stacked "Founders Weekend" headers on the guide surface
Real duplication, independent of D1. `app/lib/staff-bar/StaffBar.tsx:500` renders `staffBarApplicationLabel(application)` (→ "Founders Weekend" for `application="fw"`), and `app/fp/fw/(app)/cohort/[cohortId]/layout.tsx:82` renders `{isStaff ? "Founders Weekend · Staff" : "Founders Weekend"}` in the sticky header directly beneath it. Two elements naming the same thing, stacked.

The layout doc comment at `app/fp/fw/(app)/layout.tsx` already states the intent: *"the bar never names a weekend, only the application"* and *"what this header keeps is the context only it can carry"*. The cohort header should therefore carry **only** the cohort name and the switcher, and drop the redundant application label.

Add the assertion to `app/lib/staff-bar/__tests__/bar-wiring.test.ts`, which already exists to catch exactly this class of duplication.

**Effort: ~0.25 half-day.**

### S4 — 3.5.5 · board-link expiry after cohort end
`FW_BOARD_TOKEN_GRACE_MS = 6 * 60 * 60 * 1000` (`fw-board-rules.ts:41`), and `fwBoardTokenVerdict` (`:226`) checks `revokedAt` then expiry. **The rule is implemented and pure — it is testable without time travel.** Add a Vitest case to `fw-board-rules.test.ts` asserting rejection at `expiresAt + 1ms`, and this closes without a live run.

### S5 — 3.5.6 · board feed cache headers — **closable from source, no work**
`app/fp/fw/board/[token]/feed/route.ts:28-36` sets `Cache-Control: private, no-store, must-revalidate` and `X-Robots-Tag: noindex, nofollow` on **every** response path — 200, 404, and 503. `next.config.ts` sets the same on the subtree. The check's "not independently identified" is a test-harness gap, not a defect. Mark verified; optionally add a route test asserting the headers on all three status paths.

### S6 — 3.10.1 · server-side attestation bypass — **closable from source, no work**
Four independent layers, as designed: checkbox disables submit (`FwQuickCreate.tsx:105`), schema refuses anything but literal `true` (`fw-student.ts:77` `z.literal(true)`, mapped to `notice_not_attested` at `:144`), core re-checks (`fw-student-core.ts:260`), and `notice_attested_by` records the actor (`:314`). ### S7 — 3.15.3 · PWA manifest scope — **closable from source for the manifest half**
`public/path.webmanifest` declares `"id": "/fp"`, `"start_url": "/fp"`, `"scope": "/fp"`, `"display": "standalone"`, `"name": "First Profit"`. The remaining half — in-app navigation staying standalone — genuinely needs a physical installed iOS device. **Not a code task; queue it as device QA.**

### S8 — 3.5.9 · board memory over a long session
The board is already well-defended: bounded poll with `AbortController` (`FwBoard.tsx:48`), single in-flight poll guard (`:94`), value-comparator memo on `GridRow` (`:373`). **One real unbounded structure:** `rungKeysRef` (`:95`) is a `Set<string>` that only ever grows — one entry per celebration key for the life of the tab. At realistic event volume (tens to low hundreds of first dollars) this is negligible, so it is not worth a fix on its own, but note it if you instrument.
To actually close the check: run a 90-student board for 2h with Chrome DevTools heap snapshots at 0/30/60/120min and compare retained size. **~0.5 half-day, and it's measurement, not code.**
